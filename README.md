# Dockerfile Layer Size Companion

IntelliJ-family plugin. Shows the real, on-disk size of each
`COPY`/`ADD` layer in an open Dockerfile, inline — computed by summing
the actual file sizes of what gets copied from your local build
context, respecting `.dockerignore`. No Docker daemon, no build, no
network call: 100% static analysis of the project already open in the
IDE.

## Why it exists

An original idea, not a port of an existing competitor — validated
against this catalog's own idea-validation discipline before
being built: (1) confirmed no plugin in this catalog or in JetBrains
Marketplace does exactly this (`"docker layer size"` → 0 results on
Marketplace); (2) confirmed buildable in the ~10-day budget with
techniques this catalog already has proven — a hand-rolled line-based
Dockerfile scanner (same pattern as `NginxLexer`) and the inlay
rendering mechanism already shipped twice this session (HTTP Status
Code Inline Companion, Regex Named Group Companion). Same "apuesta
consciente sin ancla de mercado" treatment as Refactor Simulator / Test
Scaffold Companion: v0.1 ships free, no time/marketing investment
disproportionate to real demand signal until there's evidence of
adoption.

## What a number means (and when there isn't one)

This is the one rule the whole plugin is built around, so it's worth
stating plainly: **a size number only ever appears when it was
genuinely measured from real files on disk.** Nothing is ever
estimated, guessed, or fabricated to fill a gap.

- **`COPY`/`ADD` of a local file or directory** → a real number
  (`~2.3 MB`), the actual sum of `File.length()` for every file
  resolved under the source path(s), recursively for directories.
- **`COPY`/`ADD` with a `.dockerignore` present** → the same real
  number, but with excluded paths subtracted first (see
  "`.dockerignore` support" below) — marked `(respects .dockerignore)`
  so it's clear the number already accounts for it.
- **`COPY --from=<stage>` (multi-stage build)** → no number, ever.
  This copies from a *previous build stage's filesystem* — a
  container image that only exists after actually running the build.
  There is no way to know its size without running Docker. Labeled
  `copies from a previous build stage -- not calculable without
  running the build`.
- **A wildcard source (`*.jar`, `app-*.tar`)** → no number. v0.1's
  scanner does not expand glob patterns against the filesystem.
  Labeled `wildcard source -- not calculable in v0.1`.
- **A source that doesn't exist on disk** (e.g. generated by a build
  step this plugin doesn't run) → no number. Labeled `source not found
  in build context`.
- **`RUN` instructions never get a size number, period.** There is no
  way to know how many bytes a shell command will add to a layer
  without actually executing it — package downloads, compiler output,
  cache directories are all runtime-dependent. Inventing a plausible-
  looking number here would be worse than showing nothing, so the
  plugin never does it. Instead, `RUN` instructions are checked against
  a curated list of **known-expensive patterns** (see below) and
  labeled `known-expensive pattern: <reason>` when one matches — a
  qualitative flag, explicitly not a quantitative estimate.

## Known-expensive RUN patterns (curated, not exhaustive)

Each is a well-documented Docker best-practice violation (Docker's own
official guidance and the wider community consensus reflected in tools
like hadolint/dive), checked with a plain text/regex match on the
instruction's arguments — no shell parsing, no attempt to actually
understand the command:

- `apt-get install`/`apt install` without `--no-install-recommends` —
  pulls in Recommends-tier packages by default, often tens of MB of
  docs/suggested tooling never used at runtime.
- `apt-get update` without `rm -rf /var/lib/apt/lists/*` in the **same**
  `RUN` — cleaning the cache in a later `RUN` doesn't shrink this
  layer, only a later one (each Docker layer is immutable once
  written).
- `pip install`/`pip3 install` without `--no-cache-dir` — leaves pip's
  download cache in the layer.
- `npm install` without `--production`/`npm ci` — resolves
  devDependencies by default in what's often a runtime image.
- `curl`/`wget` downloading a file with no visible `rm` cleanup in the
  same `RUN` — the raw download stays in the layer even if deleted
  later.
- **2 or more consecutive `RUN` instructions** — each Docker layer has
  real per-layer storage/metadata overhead; commands that don't
  genuinely need to be separate instructions are cheaper combined with
  `&&`.

This list is deliberately **not exhaustive** — it's the well-known,
uncontroversial subset, documented honestly as a starting point, not a
claim of complete best-practice coverage.

## `.dockerignore` support (documented common subset, not the full spec)

`.dockerignore`, when present next to the Dockerfile, is applied before
summing `COPY`/`ADD` sizes — a directory a real `docker build` would
never actually send to the daemon shouldn't count toward the number
shown here. Covers what real-world `.dockerignore` files overwhelmingly
use in practice:

- Exact relative path match (`secrets.txt`).
- A bare directory/file name, matched anywhere in the tree
  (`node_modules` also matches `packages/api/node_modules`) — the
  same convention Git/Docker users already expect from a bare name
  with no slash.
- A trailing wildcard segment: a double-star segment (excludes the
  directory and everything under it, recursively) or a single-star
  segment (excludes only its direct children, not nested ones).
- A leading `*` wildcard for extensions/suffixes (`*.log`, `*.tmp`).
- A `!`-prefixed negation, re-including a path an earlier pattern
  excluded.

**Known limitation, stated honestly rather than silently wrong:**
mid-pattern globstars, `?` single-character wildcards, character
classes (`[abc]`), and the full precedence edge cases from Docker's
real `patternmatcher` reference implementation are **not**
implemented. A `.dockerignore` that only uses the common subset above
gets a correct result. One that leans on advanced glob syntax may
**over-count** (treat an actually-ignored path as included, so the
shown size is larger than the real one) — this plugin would rather
show a number that's honestly too high than one that's silently wrong
in the other, more dangerous direction (hiding real size).

## Multi-stage builds

`FROM ... AS builder` / `COPY --from=<stage>` is fully recognized by
the parser and never crashes the plugin. As explained above, the
`--from=` case always shows "not calculable without running the
build" rather than a number — this is the single case in the whole
plugin where "no number" is the *only* honest answer, not a scope
limitation that could be lifted with more engineering time.

## Known limitations (v0.1, stated honestly)

- **Build context is always assumed to be the Dockerfile's own
  directory.** A real `docker build -f sub/Dockerfile ..` can point at
  a build context directory that isn't where the Dockerfile itself
  lives — that override isn't visible from inside the editor, so v0.1
  always resolves `COPY`/`ADD` sources relative to the Dockerfile's
  parent directory. Documented here rather than silently assumed.
- **`.dockerignore` covers the common subset, not the full spec** (see
  above).
- **Wildcards in `COPY`/`ADD` sources are not expanded.** `COPY *.jar
  /app/` shows "not calculable in v0.1" rather than guessing which
  files would match.
- **`ARG`-based `FROM`/path substitution is not resolved.** A
  Dockerfile using build-args to parameterize a `COPY` source path
  isn't evaluated — the literal, unsubstituted text is what gets
  parsed.

## Why an inlay, not a gutter icon

Two rendering shapes were considered for this plugin, same design
decision every other Companion in this catalog has had to make:

- **A gutter icon** with a size shown on hover/tooltip would need a
  brand-new rendering mechanism — no plugin in this catalog has
  shipped a `LineMarkerProvider`-based gutter icon yet, so it would be
  unproven ground with no verified `verifyPlugin` track record behind
  it.
- **An inlay pinned to the end of the instruction's line**
  (`InlayModel.addAfterLineEndElement`) is the exact mechanism Regex
  Named Group Companion already ships, on top of the inline-literal
  variant (`addInlineElement`) HTTP Status Code Inline Companion
  ships — both verified 6/6 Compatible with `verifyPlugin` this same
  session. A `COPY`/`RUN` line is naturally one full statement, so
  there's no risk of two hints competing for space on the same line
  the way an inline, sub-line-position hint would need to
  disambiguate.

End-of-line inlay won on proven precedent, not because a gutter icon
would be wrong in principle — if this plugin ever needs a
richer/clickable UI (e.g. a "show reordering suggestion" action), a
gutter icon becomes the more natural choice for a future version, not
v0.1.

## Why built this way

- **No custom `FileType`/`Language` registered**, unlike Nginx
  Companion. A Dockerfile's syntax needed for v0.1 (instruction
  keyword + raw argument text, `\`-continuation) is simple enough that
  a line-based scanner over the document's plain text is sufficient —
  no completion, no syntax highlighting, no PSI tree is needed for
  what this plugin does. This also means the plugin never conflicts
  with another installed Docker-support plugin's own file type: it
  gates on filename only (`DockerfileDetector`), reading whatever
  `PsiFile`/`Document` the IDE already produced for that file,
  whatever its `FileType` is.
- **Hand-rolled Dockerfile parser (`DockerfileParser`)**, same
  "hand-roll over new dependency, small stable surface" pattern
  already proven in this catalog —
  `NginxLexer` for nginx config, `XlsxReader` for XLSX, now this for
  Dockerfile's own small, well-documented instruction grammar.
- **`.dockerignore` matching is its own small hand-rolled module**
  (`DockerignoreMatcher`), scoped explicitly and honestly to the
  common subset real-world files use (see above) rather than either
  skipping it entirely (which would silently over-count `node_modules`
  and similar routinely-excluded directories) or pulling in a full
  gitignore-style matching library for a narrow, well-bounded need.
- **Heavy computation off the EDT.** Walking the real filesystem to
  sum directory sizes runs inside `doCollectInformation` (off the
  EDT), same as every other highlighting pass in this catalog —
  only `doApplyInformationToEditor` (on the
  EDT) touches the `Editor`/`InlayModel`.
- **No Docker plugin dependency, Java or Kotlin plugin dependency —
  `com.intellij.modules.platform` only.** Because this plugin reads
  Dockerfiles as plain text (never Java/Kotlin PSI, never Docker
  plugin PSI), it has zero bundled-plugin dependency at all, and works
  identically in every IntelliJ-family IDE this catalog targets.

## Usage

Open any file recognized as a Dockerfile (`Dockerfile`,
`Dockerfile.dev`/`Dockerfile.prod`/any `Dockerfile.<suffix>`, or
`*.dockerfile`). Every `COPY`/`ADD` instruction gets an inline size
hint at the end of its line automatically. Every `RUN` instruction
matching a known-expensive pattern gets a warning-colored hint with
the specific reason. Nothing to configure in v0.1.
